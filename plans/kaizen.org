#+TITLE: Kaizen: план реализации workflow orchestrator
#+LANGUAGE: ru
#+OPTIONS: toc:3 num:nil

* 1. Цель

~kaizen~ — это *headless workflow orchestrator* для переноса и применения opinionated developer workflow между разными пользователями и машинами.

Он управляет не только установкой программ, но и конфигурацией рабочего окружения:

#+BEGIN_SRC text
- пользовательские фичи
- программы и зависимости
- dotfiles
- editor/window-manager/terminal configs
- keyboard/layout-specific настройки
- AI/dev tooling
- OS-aware варианты конфигурации
#+END_SRC

Инструмент должен решать задачу:

#+BEGIN_SRC text
Пользователь выбирает фичи:
  frontend, go, python, rust, emacs, helix, ai, mac-gui, mac-tiling, etc.

kaizen:
  1. инициализирует пользовательский config, если его ещё нет
  2. загружает выбранные фичи
  3. учитывает текущую ОС
  4. строит headless WorkflowPlan
  5. устанавливает программы через выбранный installer
  6. генерирует/обновляет данные для chezmoi
  7. применяет dotfiles/configuration через chezmoi
#+END_SRC

На первом этапе ~kaizen~ *не является package manager* и *не является resolver-ом уровня Nix*. Он не пытается сам идеально понять, что такое ~cargo~, ~node~ или ~emacs~ на каждой ОС. Вместо этого фичи описывают желаемые программы и, при необходимости, installer-specific overrides.

Первый dependency installer должен быть максимально простым в установке и запуске. Поэтому первый installer — ~upt~.

Будущие installer-ы:

#+BEGIN_SRC text
- metapac
- nix
- brew bundle
- direct providers
#+END_SRC

Dotfiles/configuration layer в MVP должен опираться на ~chezmoi~.

Главная идея:

#+BEGIN_SRC text
kaizen не является wrapper-ом над upt.
kaizen не является wrapper-ом над chezmoi.

kaizen строит WorkflowPlan.

upt — первый способ установить программы.
chezmoi — первый способ применить dotfiles/configuration.
#+END_SRC

* 2. Главный принцип архитектуры

Сначала строится *headless core*, который не зависит от CLI/TUI/GUI и не привязан к конкретному installer-у или dotfiles backend-у.

#+BEGIN_SRC text
┌────────────────────┐
│ CLI / TUI / GUI    │
└─────────┬──────────┘
          │
          ▼
┌────────────────────┐
│ kaizen-core        │
│                    │
│ config loading     │
│ init questionnaire │
│ feature loading    │
│ OS detection       │
│ atom filtering     │
│ merge engine       │
│ workflow planning  │
└─────────┬──────────┘
          │
          ▼
┌────────────────────┐
│ workflow layer     │
│                    │
│ dependencies plan  │
│ dotfiles plan      │
│ warnings           │
└───────┬────┬───────┘
        │    │
        │    ▼
        │  ┌────────────────────┐
        │  │ config layer       │
        │  │                    │
        │  │ v0: chezmoi        │
        │  │   mise.toml.tmpl   │
        │  │   + mise.lock      │
        │  │ future: other      │
        │  └─────────┬──────────┘
        │            │
        ▼            ▼
┌────────────────────┐
│ installer layer    │
│                    │
│ v0: upt            │

└─────────┬──────────┘

CLI — это только один из интерфейсов. Позже TUI и GUI должны использовать тот же core API.

Core не должен напрямую запускать ~upt~, ~metapac~, ~nix~, ~brew~, ~chezmoi~ или другие внешние команды. Core только строит данные и планы.

* 3. Что входит в MVP

MVP должен быть максимально простым, но уже учитывать обе стороны Kaizen: зависимости и конфигурацию.

Входит:

#+BEGIN_SRC text
- команда init для генерации первичного config.toml
- пользовательский config с выбранными фичами
- директория фич
- table-based feature selection
- optional disabled_atoms
- OS-aware загрузка фич
- merge TOML-файлов
- сбор [programs].packages
- сбор [mise.tools] из фич
- сбор config/chezmoi data из фич
- headless WorkflowPlan
- dry-run / plan
- install через UptInstaller
- apply через ChezmoiConfigBackend (incl. генерация mise.toml из template)
- JSON output для будущих TUI/GUI
#+END_SRC

Не входит в MVP:

#+BEGIN_SRC text
- metapac как основной installer
- MiseInstaller как отдельный crate (mise управляется через chezmoi templates)
- NixInstaller
- kaizen-level lockfile для системных пакетов (upt)
- state для safe uninstall
- automatic uninstall
- provider policy
- semantic sources database
- Steel/Scheme provider plugins
- полноценный TUI/GUI
#+END_SRC

Lockfile для dev-зависимостей решён на уровне ~mise.lock~ в chezmoi source. Версии системных пакетов (upt) не пинятся в MVP.

~metapac~ и ~nix~ должны быть предусмотрены архитектурно, но не должны блокировать первый релиз.

* 4. Термины

** Feature

Фича — это пользовательски понятный набор программ и конфигурации.

Примеры:

#+BEGIN_SRC text
frontend
python
go
rust
emacs
helix
ai
mac-gui
mac-tiling
linux-desktop
colemak
qwerty
#+END_SRC

Фичи могут пересекаться. Например, ~emacs~ и ~helix~ обе могут требовать ~ripgrep~ и ~fd~. Merge engine должен дедуплицировать зависимости.

Фича может содержать:

#+BEGIN_SRC text
- programs
- installer-specific sections
- dotfiles/config requirements
- chezmoi data
- warnings
- atoms
#+END_SRC

** Atom

Atom — опциональная внутренняя часть фичи, которую можно отключить из пользовательского конфига.

Например, фича ~frontend~ может состоять из атомов:

#+BEGIN_SRC text
node
pnpm
typescript-lsp
eslint
biome
prettier
#+END_SRC

Пользователь может включить фичу ~frontend~, но отключить atom ~eslint~:

#+BEGIN_SRC toml
[features.frontend]
enabled = true
disabled_atoms = ["eslint"]
#+END_SRC

** Program

Program — каноническое имя программы, которую пользователь хочет получить.

Примеры:

#+BEGIN_SRC text
git
ripgrep
fd
fzf
jq
helix
emacs
node
python
go
rust
#+END_SRC

На первом этапе program names передаются в ~upt~ почти напрямую.

Позже installer-ы смогут использовать overrides, например:

#+BEGIN_SRC text
node → nodejs_22 для nix
fd   → fd-find для fedora
#+END_SRC

** Config item

Config item — часть пользовательской конфигурации, которую должен применить Kaizen.

В MVP config item в основном превращается в данные для ~chezmoi~.

Примеры:

#+BEGIN_SRC text
- enable emacs config
- enable helix config
- layout = colemak
- wm = aerospace
- keyboard_manager = karabiner
- ai_tools = true
#+END_SRC

** Installer

Installer — стратегия применения dependency-части ~WorkflowPlan~.

Примеры:

#+BEGIN_SRC text
UptInstaller
MetapacInstaller
NixInstaller
BrewBundleInstaller
#+END_SRC

Первый installer — ~UptInstaller~.

** Config backend

Config backend — стратегия применения конфигурации и dotfiles.

Примеры:

#+BEGIN_SRC text
ChezmoiConfigBackend
future: HomeManagerConfigBackend
future: DirectConfigBackend
#+END_SRC

Первый config backend — ~ChezmoiConfigBackend~.

** Executor

Executor — низкоуровневый слой, который реально запускает внешние команды.

Например:

#+BEGIN_SRC text
upt install git ripgrep fd
chezmoi apply
nix profile install .#default
metapac sync
brew bundle install --file Brewfile
#+END_SRC

Installer/config backend использует executor. Core не использует executor напрямую.

** InstallPlan

~InstallPlan~ — dependency-часть плана.

Он содержит:

#+BEGIN_SRC text
- выбранные фичи
- целевую ОС
- загруженные feature-файлы
- итоговый список programs
- installer-specific sections
- warnings
#+END_SRC

** ConfigPlan

~ConfigPlan~ — configuration/dotfiles-часть плана.

Он содержит:

#+BEGIN_SRC text
- выбранные фичи
- layout/user choices
- chezmoi data
- config warnings
- dotfiles source information
- actions для config backend-а
#+END_SRC

** WorkflowPlan

~WorkflowPlan~ — общий headless результат работы core.

Он содержит:

#+BEGIN_SRC text
- InstallPlan
- ConfigPlan
- warnings
- список внешних tools, которые понадобятся
#+END_SRC

* 6. Пользовательский config

Файл:

#+BEGIN_SRC text
~/.config/kaizen/config.toml
#+END_SRC

MVP-формат использует таблицы фич, а не массив. Это нужно, чтобы пользователь мог не только включить фичу, но и настроить её: отключить отдельные atoms и позже добавить локальные расширения.

#+BEGIN_SRC toml
[features.core]
enabled = true

[features.frontend]
enabled = true
disabled_atoms = [
  "eslint",
]

[features.go]
enabled = true

[features.python]
enabled = false

[features.rust]
enabled = true

[features.emacs]
enabled = true

[features.helix]
enabled = false

[features.ai]
enabled = true
#+END_SRC

Минимально валидная фича:

#+BEGIN_SRC toml
[features.core]
enabled = true
#+END_SRC

~enabled~ обязателен. Это уменьшает магию и упрощает TUI/GUI.

~disabled_atoms~ — опциональный список atoms внутри фичи, которые нужно исключить из merge.

Пример:

#+BEGIN_SRC toml
[features.frontend]
enabled = true
disabled_atoms = ["eslint", "prettier"]
#+END_SRC

** Общие настройки

MVP должен предусмотреть простые пользовательские настройки, которые будут использоваться config layer-ом.

#+BEGIN_SRC toml
[settings]
layout = "colemak"
editor = "emacs"
window_manager = "aerospace"
keyboard_manager = "karabiner"
#+END_SRC

Пример альтернативного варианта:

#+BEGIN_SRC toml
[settings]
layout = "qwerty"
editor = "helix"
window_manager = "niri"
keyboard_manager = "xremap"
#+END_SRC

Эти значения должны попадать в ~ConfigPlan~ и затем в данные для ~chezmoi~.

** Dotfiles настройки

#+BEGIN_SRC toml
[dotfiles]
backend = "chezmoi"
source = "~/.local/share/chezmoi"  # или URL репо: https://github.com/user/dotfiles
local_source = "~/.local/share/chezmoi"
#+END_SRC

Для разработки можно использовать локальный source.

Пример текущего локального расположения dotfiles source:

#+BEGIN_SRC text
~/.local/share/chezmoi/dot_emacs.d
#+END_SRC

Важно: путь выше является примером текущей структуры dotfiles source. План не должен зависеть жёстко от конкретной локальной машины.

** Дополнительные программы

В будущем config может поддерживать пользовательские дополнительные программы:

#+BEGIN_SRC toml
[extra_programs]
packages = [
  "watchman",
  "direnv",
]
#+END_SRC

И installer-specific дополнительные пакеты:

#+BEGIN_SRC toml
[extra_installers.metapac.npm]
packages = [
  "@tailwindcss/language-server",
]

[extra_installers.metapac.brew-cask]
packages = [
  "ghostty",
]
#+END_SRC

Но для MVP достаточно:

#+BEGIN_SRC toml
[features.core]
enabled = true

[features.frontend]
enabled = true

[features.emacs]
enabled = true

[settings]
layout = "colemak"
editor = "emacs"

[dotfiles]
backend = "chezmoi"
source = "~/.local/share/chezmoi"  # путь к своим dotfiles
#+END_SRC

* 7. Setup command

~kaizen setup~ — единая точка входа. Объединяет генерацию config и интерактивный выбор фич.

** Поведение

#+BEGIN_SRC text
kaizen setup
  если config существует: открывает интерактив на текущих значениях
  если config нет:       начинает с пустыми значениями

kaizen setup --all
  включает все фичи, defaults для settings, пишет config без вопросов

kaizen setup --print
  печатает сгенерированный config в stdout, ничего не пишет
#+END_SRC

** Интерактивный флоу MVP

Для MVP — interactive CLI prompt. Последовательность шагов:

#+BEGIN_SRC text
1. Определить ОС (авто)
2. Показать список фич с описаниями:
   [ ] core     — git, ripgrep, fd, fzf, jq
   [ ] frontend — node, pnpm, TypeScript LSP
   [ ] go       — Go + gopls
   [ ] python   — Python + pyright
   [ ] rust     — Rust toolchain
   [ ] emacs    — Emacs + dependencies
   [ ] helix    — Helix editor
   [ ] ai       — AI coding tools
   [ ] tiling   — window manager
   [ ] keyboard — keyboard manager
   Space = toggle, A = toggle all, Enter = confirm
3. Задать settings (раскладка, dotfiles source)
4. Записать ~/.config/kaizen/config.toml
5. Показать: Next step: kaizen plan
#+END_SRC

** Setup API

~setup~ должен быть реализован в headless core, CLI — только адаптер.

#+BEGIN_SRC rust
pub struct SetupRequest {
    pub target_os: Option<TargetOs>,
    pub answers: SetupAnswers,
    pub all: bool,
}

pub struct SetupAnswers {
    pub features: BTreeMap<String, FeatureSelection>,
    pub settings: UserSettings,
    pub dotfiles: DotfilesConfig,
}

pub struct GeneratedUserConfig {
    pub config: UserConfig,
    pub rendered_toml: String,
}
#+END_SRC

* 8. Формат фич

Фича — это один TOML-файл:

#+BEGIN_SRC text
features/<feature-name>.toml
#+END_SRC

ОС-специфика описывается в секциях ~[os.<name>.*]~ внутри того же файла.

При загрузке kaizen делает:

#+BEGIN_SRC text
1. читает features/<name>.toml
2. мерджит общие секции
3. добавляет секции [os.linux.*] если Linux
4. добавляет секции [os.<current-os>.*]
#+END_SRC

Плюсы единого файла:

#+BEGIN_SRC text
+ все о фиче в одном месте
+ большинство фич маленькие (5-15 строк) — directory был бы избыточным
+ не нужно создавать пустые OS-файлы если различий нет
- парсер должен понимать [os.X.*]
- для очень больших OS-различий файл может стать длинным
#+END_SRC

** Простая dependency-часть фичи

Для первого прототипа основной формат — ~[programs]~.

#+BEGIN_SRC toml
[programs]
packages = [
  "git",
  "ripgrep",
  "fd",
]
#+END_SRC

~[programs].packages~ содержит канонические имена программ.

~UptInstaller~ передаёт их в ~upt install~.

Будущий ~NixInstaller~ сможет сгенерировать из них Nix package set.

** Chezmoi data (автоматическая)

Feature-файлы не объявляют ~[chezmoi.data]~ явно. Kaizen автоматически
формирует chezmoi data из включённых фич и settings.

kaizen записывает в ~<dotfiles-source>/.chezmoidata.toml~ (игнорируется git-ом через ~.chezmoiignore~).
chezmoi автоматически читает этот файл во время apply.

#+BEGIN_SRC toml
# <dotfiles-source>/.chezmoidata.toml  (генерируется kaizen)
[features]
core = true
frontend = true
emacs = true
helix = false

[settings]
layout = "colemak"
editor = "emacs"
window_manager = "aerospace"
keyboard_manager = "karabiner"
#+END_SRC

Шаблоны используют данные напрямую без промежуточных files:

#+BEGIN_SRC toml
# dot_config/helix/config.toml.tmpl
{{ if eq .settings.layout "colemak" }}
{{   template "keys-colemak.toml" . }}
{{ else }}
{{   template "keys-qwerty.toml" . }}
{{ end }}
#+END_SRC

#+BEGIN_SRC toml
# dot_config/mise.toml.tmpl
[tools]
{{- if .features.frontend }}
"npm:typescript-language-server" = "5.1.3"
{{- end }}
#+END_SRC

** Overrides

Для случаев, когда имя пакета отличается у installer-а или ОС, можно использовать overrides.

#+BEGIN_SRC toml
[programs]
packages = [
  "fd",
  "node",
]

[programs.overrides.fedora]
fd = "fd-find"
node = "nodejs"

[programs.overrides.nix]
node = "nodejs_22"
#+END_SRC

Правила:

#+BEGIN_SRC text
- если есть override для конкретного installer-а, installer может использовать его
- если есть override для target OS, installer может использовать его
- если override отсутствует, используется canonical name
#+END_SRC

Для MVP overrides можно реализовать минимально или отложить, но формат должен быть совместим с будущим NixInstaller.

** Фича с atoms

Расширенный формат позволяет разделять фичу на atoms.

#+BEGIN_SRC toml
[atoms.node.programs]
packages = [
  "node",
]

[atoms.pnpm.programs]
packages = [
  "pnpm",
]

[atoms.typescript.programs]
packages = [
  "typescript-language-server",
]

[atoms.eslint.programs]
packages = [
  "eslint_d",
]
#+END_SRC

Пользователь может отключить atom:

#+BEGIN_SRC toml
[features.frontend]
enabled = true
disabled_atoms = ["eslint"]
#+END_SRC

Тогда packages и config из ~atoms.eslint~ не попадут в итоговый ~WorkflowPlan~.

Atom не объявляет chezmoi data явно — kaizen автоматически помещает
~features.<name> = true~ в ~.chezmoidata.toml~ для всех включённых фич.

** Mise tools

Для dev-зависимостей feature-файл использует ~[mise.tools]~.
Это отдельный tier от ~[programs]~:

#+BEGIN_SRC text
[programs]    → upt  (системные утилиты: ripgrep, fd, git, niri, aerospace и т.д.)
[mise.tools]  → mise (рантаймы и dev-тулзы: node, go, rust, LSP-серверы)
#+END_SRC

~upt~ умеет ставить в том числе cask на macOS, поэтому GUI-аппы
(тайлинг, keyboard manager) тоже попадают в ~[programs]~.

Формат ~[mise.tools]~ совпадает с форматом секции ~[tools]~ в ~mise.toml~:

#+BEGIN_SRC toml
[mise.tools]
node = "lts"
pnpm = "latest"
"npm:typescript-language-server" = "latest"
#+END_SRC

Внутри atom:

#+BEGIN_SRC toml
[atoms.node.mise.tools]
node = "lts"

[atoms.typescript.mise.tools]
"npm:typescript-language-server" = "latest"
#+END_SRC

~[mise.tools]~ попадает в ~ConfigPlan~ (не в ~InstallPlan~) и используется ~ChezmoiConfigBackend~ для
формирования ~mise.toml.tmpl~.

Для ~kaizen plan~ dev-зависимости отображаются отдельно от системных пакетов.

Mise tools merge engine должен дедуплицировать tool entries (одинаковые name + version = ок,
одинаковые name + разные version = conflict).

* 9. Chezmoi configuration layer

MVP должен включать отдельный config layer на базе ~chezmoi~.

~chezmoi~ отвечает за:

#+BEGIN_SRC text
- применение dotfiles
- шаблонизацию конфигов
- OS-specific files
- layout-specific configuration
- editor/window-manager/keyboard config
#+END_SRC

~kaizen~ отвечает за:

#+BEGIN_SRC text
- выбор фич
- сбор settings
- сбор [mise.tools] из выбранных фич для ConfigPlan
- генерацию chezmoi data (фичи + settings + mise tools)
- запуск chezmoi init/apply через ConfigBackend
#+END_SRC

** Dotfiles source

~kaizen~ является фреймворком, а не хранилищем дотфайлов. Пользователь
приносит свой dotfiles source.

~[dotfiles].source~ может быть:

#+BEGIN_SRC text

** MVP команды

#+BEGIN_SRC sh
kaizen apply
kaizen apply --config-backend chezmoi
#+END_SRC

~kaizen apply~ должен:

#+BEGIN_SRC text
1. build WorkflowPlan
2. взять ConfigPlan (включая mise_tools из выбранных фич)
3. записать chezmoi-data.toml (фичи, settings, mise tools за фичу)
4. проверить наличие chezmoi
5. при необходимости выполнить chezmoi init
6. выполнить chezmoi apply
   → chezmoi рендерит mise.toml.tmpl в mise.toml с нужными тулзами
7. пользователь запускает mise install (кайзен не запускает его сам)
#+END_SRC

** Передача data в chezmoi

MVP-механизм:

#+BEGIN_SRC text
kaizen генерирует ~/.config/kaizen/chezmoi-data.toml
chezmoi.toml ссылается на этот файл через [data] секцию
#+END_SRC

Формат генерируемого файла:

#+BEGIN_SRC toml
# ~/.config/kaizen/chezmoi-data.toml
[features]
frontend = true
go = false
emacs = true

[settings]
layout = "colemak"
editor = "emacs"

[mise_tools]
# mise tools из включённых фич — передаются как дополнительные data
#+END_SRC

Дотфайлы используют ~mise.toml.tmpl~, который читает эти данные:

#+BEGIN_SRC toml
# dot_config/mise.toml.tmpl
[tools]
{{- if .features.core }}
node = "lts"
pnpm = "10.33.2"
{{- end }}

{{- if .features.frontend }}
"npm:typescript-language-server" = "5.1.3"
"npm:vscode-langservers-extracted" = "4.10.0"
{{- end }}

{{- if .features.go }}
"go:golang.org/x/tools/gopls" = "latest"
{{- end }}
#+END_SRC

~private_mise.lock~ распространяется через chezmoi как есть. ~mise~ использует его для пинов версий
только тех тулз, которые объявлены в ~mise.toml~, остальные записи в lock игнорируются.
То есть выборочность достигается не фильтрацией lock, а содержимым ~mise.toml~.

* 12. Merge rules

Merge engine должен:

#+BEGIN_SRC text
1. загружать только enabled фичи
2. применять disabled_atoms
3. объединять [programs].packages
4. дедуплицировать programs
5. сохранять стабильный порядок вывода
6. объединять [mise.tools] из всех активных фич/атомов
7. дедуплицировать mise tools (динаковые name + version = ok, разные version = conflict)
8. объединять config/chezmoi data
9. выдавать конфликт, если один и тот же config key получает несовместимые значения
#+END_SRC

** Пример дедупликации programs

Input A:

#+BEGIN_SRC toml
[programs]
packages = ["ripgrep", "fd"]
#+END_SRC

Input B:

#+BEGIN_SRC toml
[programs]
packages = ["ripgrep", "emacs"]
#+END_SRC

Output:

#+BEGIN_SRC toml
[programs]
packages = ["ripgrep", "fd", "emacs"]
#+END_SRC

** Пример конфликта detailed package

Input A:

#+BEGIN_SRC toml
[installers.metapac.mise]
packages = [
  { name = "node", options = { version = "20" } },
]
#+END_SRC

Input B:

#+BEGIN_SRC toml
[installers.metapac.mise]
packages = [
  { name = "node", options = { version = "22" } },
]
#+END_SRC

Output:

#+BEGIN_SRC text
Conflict: package metapac.mise:node requested with different options
  frontend/common.toml: version = 22
  legacy-node/common.toml: version = 20
#+END_SRC

** Пример конфликта settings

Input A (feature default):

#+BEGIN_SRC toml
# feature file default (future, если features начнут предлагать defaults)
layout = "colemak"
#+END_SRC

Input B (user config):

#+BEGIN_SRC toml
[settings]
layout = "qwerty"
#+END_SRC

User config всегда выигрывает. Конфликт возникает только если два feature-файла
задают несовместимые settings без override пользователя.

Для settings из пользовательского config можно ввести правило:

#+BEGIN_SRC text
user config has higher priority than feature defaults
#+END_SRC

* 21. Конфликт-детектор

Минимальный conflict detection:

#+BEGIN_SRC text
- same program name = dedupe
- same installer + same backend + same simple package = dedupe
- same installer + same backend + same detailed package name + same options = dedupe
- same installer + same backend + same detailed package name + different options = error
- same config key + same value = ok
- same config key + different value = error, unless user settings override feature defaults
#+END_SRC

Позже можно добавить semantic conflicts:

#+BEGIN_SRC text
- node через upt и node через metapac.mise одновременно
- rust через upt и rust через metapac.mise одновременно
- emacs через brew и emacs через nix одновременно
- emacs config enabled, но emacs feature disabled
#+END_SRC

Для MVP semantic conflicts можно не делать.

* 22. Lockfile: два уровня

** Dev-зависимости (проблема решена)

Lockfile для dev-зависимостей уже существует: ~private_mise.lock~ в chezmoi source.
~mise~ автоматически поддерживает пины версий + checksum-ы для всех тулз.

Селективность работает за счёт ~mise.toml~: отключенные фичи → тулзы не попадают
в отрендеренный ~mise.toml~ → ~mise install~ их не устанавливает
(даже если в lock есть запись).

Мейнтейнер обновляет ~mise.lock~ обычным образом:

#+BEGIN_SRC sh
mise install  # все фичи включены
# обновлённый mise.lock коммитится в chezmoi source
#+END_SRC

** Системные пакеты (upt)

~UptInstaller~ устанавливает тулзы через системный package manager. Версии определяет backend:

#+BEGIN_SRC text
apt/dnf/brew/pacman/etc. → текущие версии из репозитория
#+END_SRC

Для системных утилит (ripgrep, fd, git) пиннинг версий не критичен. Для dev-тулз — проблема
решена через mise.

В будущем можно добавить ~kaizen.resolution.toml~ для фиксации состояния
(выбранные фичи, installer, dotfiles revision), но это не нужно для MVP.

* 23. Почему state пока не нужен

State нужен для safe uninstall и rollback.

MVP не должен реализовывать автоматический uninstall, потому что без полноценного ownership tracking легко удалить пользовательские пакеты или сломать пользовательскую конфигурацию.

В MVP:

#+BEGIN_SRC text
- kaizen строит plan
- kaizen устанавливает программы через installer
- kaizen применяет config через config backend
- kaizen не делает automatic uninstall
#+END_SRC

Позже можно добавить state:

#+BEGIN_SRC toml
[packages."upt:emacs"]
existed_before = false
installed_by_kaizen = true

[configs."chezmoi:dot_emacs_d"]
managed_by_kaizen = true
backup = "..."
#+END_SRC

Но не раньше, чем появится явная команда uninstall/rollback.

* 24. Будущая поддержка metapac

~mise~ через chezmoi уже покрывает большинство случаев (npm, cargo, go, pipx утилиты).
~MetapacInstaller~ нужен для более экзотичных сценариев:

#+BEGIN_SRC text
mas     (покупки в Mac App Store)
flatpak (некоторые Linux GUI приложения)
vscode  (расширения)
#+END_SRC

~MetapacInstaller~ должен:

#+BEGIN_SRC text
1. сгенерировать ~/.config/metapac/groups/kaizen.generated.toml
   из секций [installers.metapac.*] feature-файлов
2. вызвать metapac sync
#+END_SRC

Будущий ~kaizen bootstrap --installer metapac~ может делать:

#+BEGIN_SRC sh
metapac unmanaged > ~/.config/metapac/groups/00-unmanaged.toml
#+END_SRC

Правила:

#+BEGIN_SRC text
- не перезаписывать 00-unmanaged.toml, если он уже существует
- для перезаписи требовать --force
- явно предупреждать пользователя, что это snapshot существующих пакетов
#+END_SRC

* 25. Будущая поддержка Nix

~NixInstaller~ должен быть возможен без переделки core.

Он должен использовать тот же ~InstallPlan~:

#+BEGIN_SRC text
programs + overrides.nix
#+END_SRC

Пример feature:

#+BEGIN_SRC toml
[programs]
packages = [
  "node",
  "fd",
]

[programs.overrides.nix]
node = "nodejs_22"

[programs.overrides.fedora]
fd = "fd-find"
#+END_SRC

~NixInstaller~ может генерировать:

#+BEGIN_SRC nix
{
  description = "Kaizen generated environment";

  inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";

  outputs = { nixpkgs, ... }:
    let
      system = "aarch64-darwin";
      pkgs = import nixpkgs { inherit system; };
    in {
      packages.${system}.default = pkgs.buildEnv {
        name = "kaizen-env";
        paths = with pkgs; [
          git
          ripgrep
          fd
          nodejs_22
        ];
      };
    };
}
#+END_SRC

И применять:

#+BEGIN_SRC sh
nix profile install .#default
#+END_SRC

Важно:

#+BEGIN_SRC text
NixInstaller в рамках dependency-layer устанавливает программы.
Он не управляет dotfiles, Home Manager config или nix-darwin system config в MVP.
#+END_SRC

* 26. Будущая TUI

TUI должна использовать core API:

#+BEGIN_SRC text
init_config()
list_features()
build_workflow_plan()
installer.preview()
installer.install()
config_backend.preview()
config_backend.apply()
#+END_SRC

TUI-флоу:

#+BEGIN_SRC text
1. показать список фич
2. пользователь toggles features
3. показать atoms внутри фичи
4. пользователь отключает atoms
5. выбрать layout/editor/window manager
6. показать generated plan
7. сохранить config.toml
8. выполнить install/apply
#+END_SRC

TUI не должна знать, как мерджить TOML или как строить plan.

* 27. Будущая GUI

GUI должна работать аналогично TUI:

#+BEGIN_SRC text
frontend app → calls headless engine / daemon / CLI JSON API
#+END_SRC

Для GUI заранее нужен machine-readable output:

#+BEGIN_SRC sh
kaizen init --print --json
kaizen plan --json
kaizen features --json
kaizen doctor --json
#+END_SRC

* 31. Главный критерий успеха

Первая версия успешна, если можно сказать:

#+BEGIN_SRC text
Я запустил kaizen init,
выбрал фичи frontend + emacs + ai,
выбрал layout/editor,
получил корректный WorkflowPlan для моей ОС,
увидел plan,
одной командой установил программы через upt,
и применил dotfiles через chezmoi.
#+END_SRC

Без lockfile, без state, без собственного package manager, без сложной policy-системы и без обязательного metapac.

Главный архитектурный критерий:

#+BEGIN_SRC text
Позже можно добавить MetapacInstaller, NixInstaller и другие config backends
без переписывания kaizen-core.
#+END_SRC
