# Reporting an investigated result

Use this after the source-completion self-check, or for an actual interruption/access-blocker checkpoint.

Report in the user's language:

1. Baseline: inspected revision, existing changes, contract and layout, selected target and requested dimensions, plus whether source coverage is complete within that scope.
2. Confirmed defects: required action, effective behavior, exact source locations, engine/decoder evidence where needed, and evidence level. Explain the mismatch rather than quoting a suspicious token alone.
3. Component table: selection/loading, commands/collisions, Latin behavior and Russian equivalence, with bounded result categories from the skill. A match in one navigation block does not establish whole-app compliance.
4. Separate non-defect redundancies and unresolved questions. Distinguish engine limitations, unavailable runtime checks and unread source work. Keep the same classification in every section.
5. Coverage and actual validation: link the work note and captured check results; state justified exclusions and remaining limits. For a focused audit, list the selected sources and relevant dependencies instead of repository inventory counts. Label the conclusion as a focused result; other applications and unrequested dimensions were not audited. Inventory counts are not evidence that every group was investigated.

A source-complete audit may retain precise engine questions. An incomplete checkpoint must name the interruption or failed source-access operation and the next concrete step; it is not task completion merely because it honestly admits incompleteness. Suggest repairs only for demonstrated defects. Source edits require a separate request.
