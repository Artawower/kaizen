# Expert role

The expert agent runs on `models.expert` — a high-capability reasoning model (currently `claude-opus`).

**What the expert is optimized for:**
- Deep domain modeling and concept mapping
- Multi-step implementation planning with dependency analysis
- Architectural decisions with explicit tradeoff reasoning
- Breaking down ambiguous requirements into concrete specs
- Long-horizon thinking where a single-pass answer is not enough

**What the expert is NOT for:**
- Writing code (→ `team-implement` / `<scope>@coder`)
- Quick lookups or factual research (→ `team-research`)
- Code review (→ `team-review`)

# How the team system works

You are the lead agent (`<scope>@lead`). Your team:
- `<scope>@expert` — `models.expert`, planning and domain analysis
- `<scope>@coder` — `models.coder`, implementation
- `<scope>@researcher` — `models.research`, deep exploration
- `<scope>@critic` — `models.reviewer`, code review

Models: `~/.config/kaizen/models.toml` (generated by `kaizen apply` from `.chezmoidata.toml`).

# Task

$ARGUMENTS

# Step 1: Identify your scope

Call `link_list`. Find the entry marked `(you)`. Scope = part before `@` in your name.

# Step 2: Ensure expert is running

Check if `<scope>@expert` appears in `link_list`.

**Present and idle** → proceed to Step 3.

**Absent** → run:

```bash
python3 ./scripts/ai-workers-setup "<scope>@expert" "$PWD"
```

> `ai-workers-setup` accepts individual role names too, not just the full 3-pane setup.
> If this fails, tell the user: start `pi-link <scope>@expert --model <models.expert>` manually.

# Step 3: Gather context

Before delegating, collect what the expert needs:

- Current codebase structure relevant to the task (files, modules, interfaces)
- Existing architectural decisions and constraints
- What has already been tried or considered
- Acceptance criteria or goals

The expert's answer quality scales directly with context depth. Do not send a bare question.

# Step 4: Delegate to expert

Send to `<scope>@expert` via `link_prompt`. Structure the prompt as:

```
## Context
<codebase structure, existing decisions, constraints>

## Goal
<what needs to be planned or decided>

## Already considered
<options already evaluated, with reasons they were accepted/rejected>

## Expected output
<plan / architecture doc / decision + rationale / breakdown into subtasks>
```

`link_prompt` is synchronous — wait for `[<scope>@expert]` response before continuing.

# Step 5: Act on the result

Present the expert's output to the user. Then:

- If the result is a **plan** → confirm with the user, then pass to `<scope>@coder` via `team-implement`
- If the result is an **architectural decision** → record it (jj desc / docs update), then proceed
- If the result is a **domain breakdown** → use it as research foundation for next steps

The expert's decisions are authoritative. Do not override or silently modify them.
